## 文档用途

本文档主要用于 **Skill 执行时的展开参考**。当需要设计 keep 集、判断脚本职责边界、分类编译错误、或确认完成标准时再读本文件。目标是帮助在 Kotlin Multiplatform / Kotlin Native 模块中稳定推进符号内部化，而不是记录某一次特定仓库的处理过程。重点放在：

- 如何建立可靠的 `keep` 集
- 如何设计安全的 `dry-run -> apply -> compile -> fix` 闭环
- 如何判断该修脚本、该收紧声明，还是该恢复 `public`
- 如何避免常见误判和二次踩坑

## 核心原则

- **证据优先**：保留 `public` 必须有证据来源，不能靠命名猜测
- **干净源码优先**：任何一次 apply 都应在可回滚、未污染的源码上执行
- **编译结果优先**：脚本统计只是候选，真实编译结果才是最终裁决
- **先修规则，再修残留**：如果错误说明脚本误判，优先修脚本，不在脏树上硬补
- **自动化解决共性，手工收敛边角**：批量规则只处理高频场景，少量尾部问题允许精确手工修复

## 适用场景

- 需要缩小 Kotlin Native 动态库导出面
- 需要降低链接压力、包体、导出符号规模
- 目标模块是单模块 KMP / Kotlin Native 工程，`internal` 在模块内仍可访问
- 没有可直接使用的 shrinker 插件，或需要对 shrinker 结果做人工兜底
- 已出现以下典型错误，需要围绕内部化继续收敛：
  - `public API exposes its internal type`
  - `not applicable to 'local variable'`
  - `not applicable inside ...`
  - `'actual' has no corresponding expected declaration`
  - `public-API inline function cannot access non-public-API`

## 执行前检查清单

在开始任何脚本改写前，先确认以下事项：

- **验证目标唯一**：指定单一编译验证任务，避免多个 target 同时引入噪音
- **源码可回滚**：确保当前源码不是上一轮失败结果的继续态
- **导出面可追溯**：已确认生成的 native 导出清单、桥接调用点、代码生成产物、保留规则来源的位置
- **跨平台约束明确**：`expect/actual` 成对出现的声明不能单边修改
- **已有材料可复用**：优先查看仓库中现成的候选扫描工具、批量改写工具、报告文件、错误分类工具

## keep 集最佳实践

### 一、优先级顺序

按以下顺序决定哪些符号必须保持 `public`：

1. **真实 native 导出面**
   - 优先读取生成的 native 导出头文件或等价导出清单
   - 这是最强证据来源，优先级高于包名、目录名、顶层 facade 直觉

2. **桥接入口**
   - 宿主初始化函数、桥接层显式调用的入口函数
   - 以及被宿主语言或运行时直接调用的入口声明

3. **反射与代码生成依赖**
   - 服务发现、注册入口、代理类等依赖的声明
   - 代码生成产生的注册函数、代理类、服务发现入口

4. **显式保留规则**
   - 精确名称保留
   - 模式保留
   - 构建生成常量、框架核心入口类型

5. **语言与平台配对约束**
   - `expect/actual`
   - 对外暴露的 `inline` 约束
   - 平台专有导出 contract

### 二、避免的错误做法

- 不要因为位于包根层级就整体保留 `public`
- 不要因为“看起来像入口”就保留
- 不要把“模块内 Kotlin 文件还在调用”误判为必须 `public`
- 不要让 keep 集只保留结果，不保留原因

### 三、推荐输出

建议每个保留项都能追溯到原因，例如：

- exported in generated native header
- referenced by native bridge
- generated by codegen
- matched by pattern-based keep rule
- required by platform contract

## 脚本设计最佳实践

### 一、顶级声明识别

对 Kotlin 批量改写来说，最关键的是 **只改真正的顶级声明**。

优先级建议：

1. AST / 语法级方案
2. 列 0 + 明确声明模式
3. 保守的文本匹配

不推荐：

- 用花括号深度近似顶级作用域
- 用缩进和花括号混合做复杂猜测
- 对嵌套声明默认乐观处理

### 二、必须覆盖的边界 case

脚本至少要显式考虑以下声明形态：

- `fun interface`
- `typealias`
- `annotation class`
- `final class`
- 顶级 `val` / `var`
- 扩展函数
- 泛型函数
- 嵌套 `interface`
- `expect/actual`
- `inline` 函数

### 三、脚本职责边界

脚本更适合做：

- 候选扫描
- `public -> internal` 的共性改写
- 基础报告输出
- 错误日志分组辅助

脚本不适合硬编码解决：

- 少量业务特例
- 复杂暴露链决策
- 所有嵌套语法边角
- 需要语义判断的 contract 恢复

## 推荐执行流程

### 1. 分析候选面

- 运行候选扫描工具
- 输出候选声明和保留原因
- 确认本轮目标模块、文件范围和估算修改规模

### 2. dry-run

- 运行 internalize dry-run
- 只看统计不够，必须抽查若干边界 case
- 至少抽查以下内容：
  - `fun interface`
  - `typealias`
  - `annotation class`
  - 顶级属性
  - `expect/actual`
  - 嵌套声明文件

### 3. 在干净源码上 apply

- 先回到干净源码
- 再执行 apply
- 同步生成改动摘要和机器可读报告

### 4. 编译验证

- 立即执行唯一验证任务
- 保留完整日志，不只看 `tail`
- 编译日志建议落盘，便于错误聚合与后续复盘

### 5. 错误分类收敛

- 先按类别分组，而不是逐条修
- 推荐配合错误分类脚本、日志分组工具或自定义 summarizer 使用
- 优先判断：
  - 是脚本误判
  - 还是 public 暴露链未闭合
  - 还是语言规则约束

### 6. 精确补洞

- 对共性错误回到脚本修正
- 对少量尾部错误，允许手工精准修复
- 修复后重新回到干净源码复跑，避免补丁叠补丁

## 常见错误与处理建议

| 错误现象 | 常见根因 | 优先动作 |
|---|---|---|
| `not applicable to 'local variable'` | 顶级声明识别过宽，误伤局部变量或 lambda 内声明 | 回滚源码，修脚本选择器 |
| `not applicable inside ...` | 误改嵌套声明、`interface` 或 `annotation class` 内部成员 | 缩小作用域，跳过嵌套上下文 |
| `public API exposes its internal type` | public 暴露链未闭合 | 优先判断暴露方是否也应 `internal` |
| `public-API inline function cannot access non-public-API` | public `inline` 调用了 internal 成员 | 收紧 `inline` 函数，或恢复被调用符号 |
| `'actual' has no corresponding expected declaration` | `expect/actual` 可见性不一致 | 成对检查并统一修改 |
| 顶层 facade 大量保留为 public | 把包根层级错当成导出面 | 改为基于生成导出头文件和真实调用推导 keep 集 |

## 何时该修脚本，何时该手工修

### 优先修脚本的情况

- 同类错误在多个文件反复出现
- 边界 case 明显属于语法识别缺陷
- 错误来自声明选择器，而不是业务 contract
- 继续手工修会掩盖根因

### 允许手工修的情况

- 剩余错误数量已经很少
- 问题是局部暴露链，而不是规则层面缺陷
- 该位置带有明确业务含义，脚本不适合自动决策
- 修复动作非常确定，例如：
  - 把模块内属性改成 `private`
  - 把辅助 DTO / 转换函数改成 `internal`
  - 恢复个别必须公开的 contract

## 完成标准

满足以下条件后，才可认为这一轮内部化完成：

- 目标编译任务通过
- 本轮新增改动都能被脚本规则或手工补丁解释
- `public` 保留项都能说明证据来源
- 报告文件可审计、可复跑、可复盘
- 手工修复项数量有限且集中，不存在大面积“救火式”源码修补

## 推荐沉淀的辅助能力

后续如果继续完善这套 Skill，优先考虑沉淀以下能力：

### 1. 运行 manifest

建议记录：

- git commit / dirty state
- 编译目标
- keep 集来源摘要
- dry-run / apply 数量
- 手工修复文件列表
- 最终编译结果

### 2. 回归样本集

建议维护最小 Kotlin 样本，覆盖：

- `fun interface`
- `typealias`
- `annotation class`
- `final class`
- 顶级属性
- 扩展函数
- 嵌套声明
- `expect/actual`
- `inline` + internal 访问

### 3. 暴露链分析辅助

可进一步增加半自动诊断：

- 定位暴露方声明
- 定位被暴露 internal 类型
- 给出“收紧暴露方”或“恢复类型可见性”的建议

## 经验提炼

- 用花括号深度近似顶级声明，通常容易误改局部变量和嵌套成员
- 将 keep 集从包名 / 目录猜测，收敛到真实导出集合后，误判通常会明显下降
- 更稳的路径通常不是继续扩大脚本改动面，而是“修规则 + 分类收敛 + 少量精确补洞”
- 对仅模块内使用的辅助 DTO、转换函数、私有实现细节，继续收紧为 `private` / `internal` 往往是高收益动作
